01 / 标准 C++ 与虚幻引擎的反射

在现代计算机语言生态中，C#、Java 等语言拥有原生反射能力。程序可以在运行时查询自身的类名、成员变量与方法签名，进而完成动态调用与序列化。

而标准 C++ 坚持零成本抽象的设计哲学。它提供的 RTTI 能力有限，无法直接枚举一个类的全部属性，也不能按名称动态调用任意成员函数。

反射并不是让编译器猜出一切，而是将类型的信息，提前写进程序能够读取的数据结构。

理解 UHT 的一个入口

为了兼顾原生性能与动态能力，虚幻引擎引入了 UHT（Unreal Header Tool）。它读取带有反射标记的声明，为普通的 C++ 类型生成额外的描述信息和接口。

  • 按名称查找类、属性与函数。
  • 通过统一的属性描述完成序列化。
  • 为编辑器、蓝图和网络复制提供类型信息。

02 / UHT 在构建流水线中的位置

点击 Build 之后，UBT 负责组织整个构建任务。在调用 C++ 编译器之前，它先运行 UHT，处理工程中需要参与反射的头文件。

扫描、校验、构建与生成

UHT 关注的是类和成员的声明。它识别 UCLASS()、UPROPERTY() 与 UFUNCTION() 等标记，检查说明符，再构建用于生成代码的类型模型。

阶段主要工作产出
扫描识别声明与反射标记语法信息
校验检查类型和说明符约束有效声明
构建组织类型与继承关系反射模型
生成输出胶水代码和注册代码生成文件

这些生成文件最终仍然交给普通 C++ 编译器处理。对编译器而言，反射所需的数据与接口也只是参与编译的 C++ 代码。

03 / generated.h：编译期的接口

对于参与反射的类型，生成头文件应位于其他 include 之后。类中的 GENERATED_BODY() 为生成代码提供展开位置。

MyInventoryComponent.h
// 反射接口示例
#pragma once

#include "CoreMinimal.h"
#include "Components/ActorComponent.h"
#include "MyInventoryComponent.generated.h"

UCLASS(ClassGroup=(Custom),
       meta=(BlueprintSpawnableComponent))
class MYPROJECT_API UMyInventoryComponent
    : public UActorComponent
{
    GENERATED_BODY()

public:
    UPROPERTY(EditAnywhere, BlueprintReadWrite,
              Category="Inventory")
    int32 Capacity = 20;

    UFUNCTION(BlueprintCallable,
              Category="Inventory")
    bool AddItem(int32 ItemID);

    UFUNCTION(BlueprintPure,
              Category="Inventory")
    int32 GetCapacity() const;
};

这段声明描述了组件的公开能力。UHT 将反射标记转换为可供引擎查询的信息，让编辑器和蓝图能够找到这些属性与函数。

NOTE

.generated.h 与 .gen.cpp 是同一套生成流程的不同产物。阅读时把接口声明和注册实现放在一起看，会更容易理解它们的配合。

04 / 从声明到运行时

编译阶段建立好类型描述，运行阶段再把这些信息注册到引擎的类型系统中。编辑器、序列化与蓝图由此获得了统一访问 C++ 对象的入口。

回到最初的问题：反射能力来自一条完整的协作链路。声明提供意图，UHT 生成描述，编译器生成机器码，引擎在运行时使用这些信息。
